Champions Field · the build log, retold

An AI built this game in one evening. Here is the play-by-play.

On September 4, 2026, a teacher in Honolulu pasted an 800-word wish list into an AI coding tool at 5:29 pm. By 9:56 pm a playable rocket-car soccer game was live on the web, with touch controls for phone-sized screens (tested in an emulator; no real phone yet). The human typed nine messages the whole evening. This page walks through what the AI actually did in between, minute by minute, for readers who have never written a line of code.

The code itself is a rough recreation, and it says so about itself. What makes the evening worth studying is the speed, and the habits the AI kept while going fast: reading the rules first, checking its own work with screenshots, asking a second AI to find problems, and stopping to ask before publishing.

Who was on the field

AI coding tools now work as small teams. In these logs each helper got a random human first name, which makes the transcript read like an office. The names are labels, nothing more.

  • Justinthe human
    A teacher who runs a lot of these tools. He wrote the brief, checked in a few times, said yes or no to publishing, and otherwise stayed out of the way.
  • Astralead agent · gpt-6-astra
    Read the brief and the house rules, wrote nearly all the code, ran the game in a real browser, took screenshots, decided what to fix next, and wrote the reports. When the work split, Astra handed pieces to helpers and reviewed what came back.
  • Pam, Jim, Darrylimplementers · gpt-5.6-terra
    Short-lived helpers given one bounded job each: fix a physics defect, fix the bot, fix the camera. They shared the same folder as Astra, so their edits appeared instantly.
  • Oscar, Dwightreviewers · gpt-5.5
    Fresh-context reviewers on a different model. They never saw Astra's reasoning. Their whole job was to read the code, poke at the physics, look at the screenshots, and report problems. They found real ones.
  • The Guardiansafety referee · codex-auto-review
    An automatic model that judged each risky action before it ran: installing software, starting servers, writing shared files, publishing. It rated risk and checked whether the human had actually authorized it. It said yes 102 times and no 3 times.

Decoder

A few words that come up constantly below.

Repository (repo)
The project's folder, with a full history of every change. This one lives on GitHub, a website for hosting code.
Commit
A saved snapshot of the code with a short label. Nothing leaves the laptop until it is also pushed.
Push
Uploading commits to GitHub so they are public. In this project, pushing also republishes the live game.
Branch
A side copy of the code for trying things out. Merging brings it back into the main line.
Dev server
A tiny local web server so the game can be opened in a browser at an address like 127.0.0.1:5173. Only visible on the one machine.
Test
A small program that checks one rule automatically, such as "a ball fully across the goal line scores once." Green means pass.
Physics engine
A library (here, Rapier) that handles gravity, bouncing, and collisions so the game does not have to invent them.
Three.js
A library for drawing 3D scenes in a web browser.
Subagent
A second AI started by the first one to do a piece of the work, then report back.
GitHub Pages
GitHub's free hosting: it turns a repository into a public website. Here it republishes the game on every push.
Token
The unit AI models read and write in, about three-quarters of a word.

What to notice

If you are learning how these tools work, the code is the least interesting thing on this page. Watch the habits.

  1. It read the rules before it wrote code. Every session opened by reading the project's instruction files and the previous handoff note. Nothing about the game itself happened in the first minute. (5:29, 8:55, 9:16, 9:45)
  2. It looked at its own screenshots. Not "the code should render a car" but "here is a picture, and the hood is hollow." The inward-facing triangles at 5:56 and the camera dragged into the stands at 9:26 were both caught by eye.
  3. It measured instead of asserting. Frames per second, mesh counts, flip timers, test counts. When a number got worse (56 to 53 fps), it reported both.
  4. It got second opinions from a different model that had not seen its reasoning. Five times. The reviewers found a false-green test setup, a boost bug that corrupted aerial control, and a collision box floating below the car. The builder never graded its own work.
  5. It checked the reference before trusting a plausible fix. Pam's braking-while-boosting change felt right and was wrong. Reading the open-source reimplementation of the original's physics is what caught it. (9:00)
  6. It debugged its own tools as often as the product. A test page sending keys to the wrong element, a mobile script with malformed touch events, a locked browser, a stale cached file. Watching an agent work looks a lot like watching someone fix their own equipment.
  7. It stopped before publishing, every time. Four reports ended with a version of "uncommitted, nothing published." All four pushes happened only after Justin typed a go-ahead. The one time it tried to authorize itself, at 6:08, the safety referee blocked it.
  8. Two agents in parallel needed a referee. The GitHub thread did all the setup and was still not allowed to push, because the "yes" was typed in a different conversation. Trying to route around the denial by asking another agent to push was denied too. (6:57)
  9. It never claimed the thing it did not achieve. The brief asked for "nearly identical." Every report said "approximation." The shipped documentation says the car is "a recognizable procedural buggy, not a legitimate Octane mesh."
  10. It wrote notes for whoever came next. The handoff document is longer than most of the code files and includes a list of bugs already fixed so they are not re-introduced.

Honest limits

It is a playable rocket-car soccer game with a similar layout, and that is all it is. The car, stadium, effects, and handling are custom approximations of the original. No human had played a full five-minute match when the evening ended, and the agent said so.

The code is fast code, not teaching code. The source is dense: some lines run past 1,600 characters, and eighteen files hold about 105 kilobytes in roughly a thousand lines. It was written to be run, not to be read by a student. If you open it expecting a tutorial, you will be disappointed. If you open the handoff and verification documents instead, you will find the story.

It was not cheap. Roughly 42 million tokens were read across the evening, the great majority of them the same project files re-read each turn from cache, plus about 200,000 tokens written. The safety referee's own reading added up to a few million tokens on top of the builders'. What this costs depends entirely on the plan behind it.

Nine messages is not zero supervision. Justin knew what to ask for, wrote a detailed brief, keeps a set of house rules that every agent reads on entry, and said no to publishing until he had played it. The speed is real. So is the setup that made it safe to go fast.
